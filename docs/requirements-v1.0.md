# Dify Agent：需求规格与开发规划

版本：v1.0  
整理日期：2026-10-09  
项目名称：Sierra（用户于 2026-10-10 确定）  
文档用途：记录头脑风暴结论，作为第一版开发、验收和后续变更的共同依据。

> 文档中的“已确认需求”来自本次讨论；“建议设计”是开发方案，不表示已经实现或已经完成技术验证。“待确认／待验证”必须保留为未解决项，不得用默认值冒充用户决定。

## 1. 产品定位与目标

为了解 Dify 的同事或开发者提供一个专业搭建助手。用户选择 Dify 应用类型，描述业务需求并提供参考材料；助手深入沟通、提出具体方案，确认后准备资源、生成 DSL、导入 Dify、试跑和修复，交付可继续调整的成果。

第一版在用户自己的电脑上运行，通过浏览器使用，按一个人从头到尾完成任务设计。未来可部署给同事使用，但多人协作不是第一版的必要条件。

核心价值是减少重复搭建、配置和排错工作。允许用户完成部分精细调整和真实接口调试。“约 20% 人工微调”是期望，不作为按工作量计算的硬性验收指标。验收以具体功能、样例和待办为准。

项目同时用于积累真实工程经验和面试展示，但功能设计首先服务真实 Dify 搭建需求。

## 2. 已确认的核心决定

| 编号 | 决定 |
| --- | --- |

| D-02 | 首要入口是从零创建应用，根据描述快速搭建，允许参考已有 DSL。 |
| D-03 | 覆盖多种业务工作流，不只做知识问答。 |

| D-11 | 助手生成工作流内代码节点的代码，并纳入检查和试跑。 |

| D-13 | 接受模拟数据作为阶段性成果，模拟依赖和未验证部分必须明确标注。 |
| D-14 | 无法连接 Dify 时可以生成待验证的 DSL，保留进度，之后继续。 |
| D-15 | 支持持续修改、再次试跑；以用户当前实际使用的版本为基础，保留人工调整。 |
| D-16 | 保存单人任务进度、确认记录和版本，支持后续继续。 |
| D-17 | 明确的小问题自动修复；多次无进展、改变确认方案或达到投入上限时暂停说明。 |
| D-18 | 能力或条件不足时说明缺口、替代方案、体验／费用／人工影响，由用户决定。 |
| D-19 | 未确认前不能悄悄删减功能，再宣称完成。 |
| D-20 | 外部服务、网站和业务系统的额外开发不在核心范围内；可以提出方案和接入条件。 |
| D-21 | 采用对话加任务工作台的网页形态；当前原型可作为暂定界面方向。 |
| D-22 | 设置中支持接入模型服务，用户可以配置自己的 API Key；支持考虑主模型与轻量模型分工。 |
| D-23 | 开发过程中可以将适合独立完成的任务交给较轻量模型，关键设计和整合由主 Agent 负责。 |

## 3. 范围与概念

### 3.1 应用类型与业务运行方式

应用类型由用户选择。Workflow、Chatflow、Agent 等名称和 DSL 结构，应以目标 Dify 版本实际支持的类型为准。具体首批类型清单在环境验证阶段锁定，并在界面显示支持状态。

助手不能因为某种类型更容易实现就自动更换类型。发现不匹配时，解释问题、提出方案，等待用户选择。

“对话、单次任务、批量、自动触发、人工参与”是业务需求维度，不是五种额外产品。它们可以组合。

| 场景 | 必须澄清的业务问题 |
| --- | --- |
| 连续对话 | 是否记住上下文；什么时候追问；什么时候结束或转人工。 |
| 单次任务 | 输入是什么；处理规则是什么；一次执行的结果是什么。 |
| 批量处理 | 如何分项；单项失败是否继续；如何汇总成功和失败。 |
| 自动触发 | 何时启动；从哪里获取输入；输出交给谁；相关条件是否已具备。 |
| 人工参与 | 谁审核或补充；需要看什么；通过、拒绝、未回复时怎么处理。 |

覆盖目标是能识别这些需求并规划对应方案。实际生成、导入和运行能力受目标版本、节点、插件、权限及外部条件影响；缺口必须走协商流程。

### 3.2 纳入核心范围

- 从零创建应用，允许基于参考材料生成。
- 当前搭建任务中的持续修改、版本恢复和重新验证。
- 模型、提示词、知识库、检索、条件、代码和接口等流程内部配置。
- 在目标环境支持且用户确认后，准备知识库、连接已有接口、创建或更新目标应用、执行试跑。
- 文件、配置说明、运行报告和人工调试指南的交付。

### 3.3 不纳入第一版核心范围

- 为客户完整开发独立网站、审批系统、数据库服务或其他外部业务系统。
- 保证所有 Dify 版本、全部插件和所有节点无差异支持。
- 保证跨客户环境无损迁移或自动复原所有资源。
- 多人同时编辑、企业角色权限和团队审批体系。
- 自动训练一个新大模型。
- 无限制自主执行、修复和消费模型费用。

复用或调用客户已有外部系统属于接入工作；新建外部系统属于额外开发。边界有疑问时说明后由用户确认。

## 4. 功能需求

### 4.1 任务与应用类型

| ID | 精确需求 | 验收依据 |
| --- | --- | --- |
| FR-01 | 创建任务必须由用户主动选择应用类型和目标环境；支持尚未接通的环境。 | 未选类型不能进入生成；断开环境只能产出标注为待验证的成果。 |
| FR-02 | 每个任务有独立的需求、对话、材料、配置、执行记录、版本和成果。 | 切换任务不会混用另一任务的数据或确认记录。 |
| FR-03 | 用户明确指定类型后，所有生成、检查和导入均按该类型处理。 | 类型冲突被提示；不存在静默替换类型。 |
| FR-04 | 支持保存和继续单人任务，恢复当前阶段及待处理事项。 | 关闭并重开应用后，能看到历史进度并继续。 |

### 4.2 需求访谈、材料和冲突

| ID | 精确需求 | 验收依据 |
| --- | --- | --- |
| FR-05 | 支持文字描述及多形式参考材料入口；识别无法处理的格式并说明替代输入方式。 | 可登记材料来源；解析失败有提示，不把空内容当已读取。 |
| FR-06 | 对材料内容记录来源，区分用户明确要求、参考建议和助手提出的假设。 | 用户能追溯主要规则来自哪里。 |
| FR-07 | 每份重要参考须确认参考程度：借鉴思路、保留指定部分或严格复现。 | 未明确参考程度时追问；指定保留项在检查中被核对。 |
| FR-08 | 使用标准说明单收集信息；按场景补问专项问题。 | 不相关场景的问题不会全部机械询问。 |
| FR-09 | 关键规则缺失或矛盾时追问；用户不清楚时提出具体草案和例子。 | 用户确认前，草案仍标为建议。 |
| FR-10 | 材料、当前描述、历史确认之间冲突时，指出影响、推荐处理并请用户裁定。 | 未解决的关键冲突阻止搭建。 |
| FR-11 | 已确认内容可复用；新增要求只重新确认受影响部分。 | 继续任务时不要求从头复述所有需求。 |
| FR-12 | 形成一份明确、可编辑的最终需求说明，确认记录绑定具体版本。 | 能回答“用户确认的是哪一份方案”。 |

多形式材料是产品目标。首批支持的具体扩展名、单文件大小、扫描文档 OCR 和图片理解能力，在解析器及模型验证后明确，不把上传入口等同于已能理解文件。

### 4.3 搭建准入标准

正式准备或变更目标资源、生成完整应用前，必须具备下列信息。需求讨论、资料读取、检查和方案草拟可在准入前进行。

| 字段 | 必须明确的内容 |
| --- | --- |
| 目标和范围 | 为谁解决什么问题；本次哪些功能必须完成；哪些不在本次范围。 |
| 输入 | 字段、文件或事件的形式；必填条件；单条或批量；缺失时如何处理。 |
| 输出 | 内容和结构；文件或消息等形式；输出交给谁或哪里。 |
| 业务规则 | 分类、分支、计算、生成和追问等行为依据；不得违反的约束。 |
| 数据与依赖 | 使用的材料、库、模型、接口、插件；实际可用、待补充或模拟的状态。 |
| 类型、环境与配置 | 用户所选类型；目标环境信息；具体配置方案及资源操作方案。 |
| 异常处理 | 关键失败、信息不足和无结果时的行为；复杂任务的专项策略。 |
| 验收样例 | 正常输入、关键分支和相关异常；每个样例的预期行为或结果。 |

准入规则：

1. 不适用项可以明确标记“不适用”，不能留作未经解释的空白。
2. 影响业务、流程或验收的未知项及冲突，必须解决。
3. 缺少资源不等于需求不清楚。可以确认模拟方案或待补条件后继续。
4. 完整需求、具体配置和资源操作都需要确认；可以集中确认，有异议时展开讨论。
5. 用户确认范围、选择或依赖发生变化时，相关确认和测试状态失效，需重新确认和验证。

### 4.4 模型、节点和资源配置

| ID | 精确需求 | 验收依据 |
| --- | --- | --- |
| FR-13 | 集中展示模型名称、适用节点、参数、知识库及检索方式等具体配置。 | 展示实际选择，不只展示“高质量”之类抽象偏好。 |
| FR-14 | 每项关键选择说明理由；信息不足时提出建议并确认。 | 用户能查看理由并修改单项。 |
| FR-15 | 仅引用目标环境已发现或用户明确提供的资源；无法确认存在的资源标为待创建或待映射。 | 不编造可用模型、知识库、插件或接口 ID。 |
| FR-16 | 新增、复用或修改资源前，列出动作、目标和影响，由用户确认。 | 执行记录能够对应确认方案；新增影响触发重新确认。 |
| FR-17 | 发现版本或能力限制，说明可完成部分、缺口及替代方案。 | 用户能选择接受、补齐条件或缩小范围。 |
| FR-18 | 更换环境时重新核对类型、模型、库、插件、凭据及资源引用。 | 原环境资源 ID 不被未经映射直接认为在新环境可用。 |

### 4.5 知识库准备

| ID | 精确需求 | 验收依据 |
| --- | --- | --- |
| FR-19 | 已明确知识库时核对适用范围和可用性；多库时提出选库建议并确认。 | 选择有依据，用户确认具体库。 |
| FR-20 | 只有原始资料时，承担大部分可读取性检查、重复／版本／矛盾识别和组织工作。 | 有资料处理结果和未解决问题清单。 |
| FR-21 | 建议资料分组、知识库准备与检索配置，确认后在可用环境中执行。 | 创建、上传、索引等实际结果有记录，失败不伪装成功。 |
| FR-22 | 业务事实冲突由用户裁定，不仅按文件日期自动决定正确内容。 | 冲突保留来源和处理决定，不静默删除事实。 |
| FR-23 | 使用代表性问题验证检索结果；区分检索无答案和检索失败。 | 能查看问题、检索证据和对应处理行为。 |

知识库准备功能属于目标需求。可用管理接口、权限、索引模型和具体检索选项，要在目标 Dify 环境验证后实现。

### 4.6 流程、DSL 和代码生成

| ID | 精确需求 | 验收依据 |
| --- | --- | --- |
| FR-24 | 根据确认说明生成所选类型的流程、提示词、节点配置、变量和连接。 | 需求中核心功能有对应实现；指定保留项有检查结果。 |
| FR-25 | 支持 Dify 版本与应用类型对应的生成规则，记录目标版本。 | 不混用不同版本字段或类型结构。 |
| FR-26 | 检查 YAML、必要字段、节点 ID、连接、变量引用、数据类型和关键路径。 | 可定位错误到节点／字段；校验失败不宣称可导入。 |
| FR-27 | 遇到代码节点，助手生成符合业务规则的代码，并执行适当检查及样例验证。 | 正常与相关异常样例有结果；不能只把代码文本存在视为可运行。 |
| FR-28 | 根据批量、分支、上下文、触发、审核等需求采用目标环境支持的结构。 | 不支持的结构显式报告并协商。 |
| FR-29 | 目标环境不可访问时可生成完整度明确的草稿或待验证 DSL。 | 文件和界面明确显示尚未真实导入／试跑。 |
| FR-30 | 对真实数据、模拟依赖、待填配置和未验证节点保持标记。 | 交付包能定位需要人工接入的位置。 |

代码节点内部的数据清洗、格式转换、计算与合并属于工作流内容；另建外部服务不在范围内。

### 4.7 导入、试跑与修复

| ID | 精确需求 | 验收依据 |
| --- | --- | --- |
| FR-31 | 在有连接条件且获用户确认的目标环境执行约定的导入及资源操作。 | 使用实际返回值、应用标识和结果，不用模型口述代替执行证据。 |
| FR-32 | 对确认样例执行真实试跑，记录输入、预期、实际输出、状态和关键错误。 | 主流程及关键分支能分别检查。 |
| FR-33 | 信息不足、无检索结果、接口失败等行为需主动建议、确认并纳入样例。 | 异常处理有明确预期，未提出时由助手补问。 |
| FR-34 | 根据错误自动修复明确的小问题，并重新执行受影响检查。 | 修复保持已确认业务目标，不通过删除关键功能使测试过关。 |
| FR-35 | 反复无进展、需要改确认方案或达到投入上限时暂停，说明成功／失败部分和下一步。 | 不无限重试，不擅自改方案。 |
| FR-36 | 支持用户暂停、补充信息后继续；暂停应阻止派发新的执行步骤。 | 当前步骤是否完成或无法立即取消有明确状态。 |
| FR-37 | 记录模型调用用量、执行耗时、重试及费用估算，说明估算依据或不可用项。 | 不把模拟数字当真实账单；停止条件由程序落实。 |

连续无进展次数、时间上限、费用上限和各类超时的正式默认值尚未确定。原型数值只是演示，不是已确认要求。

### 4.8 修改、版本与恢复

| ID | 精确需求 | 验收依据 |
| --- | --- | --- |
| FR-38 | 当前任务可以持续讨论、调整、生成和重新试跑。 | 用户看过结果后可修改，不需要每次重开任务。 |
| FR-39 | 以用户当前实际应用／最新提供的 DSL 为基础，保留人工修改。 | 无法取得最新版本时要求用户提供，不静默使用旧文件覆盖。 |
| FR-40 | 记录需求、配置、DSL、确认记录和验证结果之间的版本关联。 | 可以追溯一个成果对应哪次需求和确认。 |
| FR-41 | 修改前保存可恢复版本，展示主要变化及受影响的验证项。 | 恢复后保留历史；旧测试结果不会直接冒充新版本通过。 |
| FR-42 | 环境或资源发生变化时重新核对依赖和测试状态。 | 已确认的映射变化会被提示。 |

版本恢复首先是项目文件和方案的恢复。涉及外部应用或知识库的覆盖、还原需要另行列明操作和影响，不承诺自动撤销所有外部副作用。

### 4.9 模型接入与任务分工

| ID | 精确需求 | 验收依据 |
| --- | --- | --- |
| FR-43 | 用户能添加、编辑、删除模型服务配置，包含名称、供应商、地址、模型标识和 API Key。 | 后台完成实际调用，界面可显示明确的连接错误。 |
| FR-44 | 使用支持的供应商适配器及自定义兼容接口；协议与能力不兼容时报告。 | 不能承诺任意地址只填 Key 就可使用全部功能。 |
| FR-45 | 验证任务所需的文本、工具调用、结构化输出及图片处理等能力。 | 不把一次简单聊天成功视为全部 Agent 能力通过。 |
| FR-46 | 区分搭建助手的模型配置与生成应用在 Dify 中使用的模型配置。 | 两者可不同，费用与调用记录分别说明。 |
| FR-47 | 考虑主模型、轻量任务及图片处理的分工，失败时可按规则升级处理。 | 保留任务路由和升级记录，关键判断不被低质量结果直接替代。 |
| FR-48 | 控制上下文、重试和子任务数量，程序可完成的确定性检查优先由程序执行。 | 比较总用量、费用和成功率，不承诺子 Agent 必然省 Token。 |

多模型路由属于规划中的优化能力，安排在基本链路稳定后实现。用户不必先配置多个模型才能创建第一个任务。同一模型可以承担多个用途。

凭据由本机后台使用；保存机制需在开发设计中明确，禁止进入任务交付文件和普通日志。当前原型不接收真实 Key，不代表正式版已具备凭据管理能力。

## 5. 前端需求

暂定采用三栏结构：左侧任务列表，中间对话，右侧工作台。设置使用独立页面或弹窗。原型样式可调整，功能与状态语义保持一致。

| 页面／区域 | 必需功能 |
| --- | --- |
| 新建任务 | 用户主动选类型、选目标环境，填写名称并进入讨论。 |
| 任务列表 | 显示名称、类型和当前状态；可恢复历史任务。 |
| 对话 | 文本沟通、材料上传、助手追问、方案解释和修改反馈；支持流式输出。 |
| 材料区 | 来源、解析状态、参考程度、冲突及用户处理决定。 |
| 需求页 | 标准说明单、缺失项、未解决冲突、确认或编辑入口。 |
| 配置页 | 具体节点、模型参数、知识库、资源操作和选择理由；支持集中确认与局部修改。 |
| 流程预览 | 展示主要节点、分支和说明；不要求首版复制整个 Dify 画布编辑器。 |
| 执行／试跑页 | 阶段进度、真实操作结果、样例对比、错误修复、暂停和继续。 |
| 版本页 | 查看变化、恢复方案、提供人工修改后的最新 DSL。 |
| 交付页 | 下载 DSL 与说明，查看验证等级、模拟依赖和待办。 |
| 模型设置 | 供应商、地址、Key、模型、用途、连接和能力测试。 |
| 环境设置 | 公司／客户环境配置、版本、连接状态、资源可用性。 |
| 用量设置 | 修复、时间、费用上限；实际用量与费用估算。 |

确认记录必须关联明确方案版本。模糊的“可以”只有在上下文唯一指向具体方案时才可转为确认；多份待确认方案同时存在时需要澄清。

执行进度展示操作、结果和下一步，不要求展示模型内部推理过程。界面必须区分真实结果、模拟结果、待验证结果。

## 6. 验收与交付状态

### 6.1 通用完成条件

标记“本次约定范围已完成”必须同时满足：

1. 核心需求都有对应实现，未删减用户尚未同意放弃的功能。
2. DSL 已成功导入约定的目标 Dify 环境。
3. 已确认的主流程和关键分支样例通过。
4. 模拟依赖、待接入条件和人工调试项明确列出。
5. 成果、配置、测试及确认记录指向同一版本。

“可以导入”与“已经导入成功”、“结构校验通过”与“运行结果正确”必须分别记录。

### 6.2 状态表达

| 状态 | 使用条件 | 必须说明 |
| --- | --- | --- |
| 草稿／待验证 | 尚未完成真实导入或运行，或目标环境不可访问。 | 已做检查、未做检查及恢复条件。 |
| 阶段性成果 | 已有可用部分，但本次核心验证或关键功能仍缺失。 | 成功部分、失败部分、模拟依赖及待办。 |
| 本次约定范围已完成 | 满足通用完成条件。 | 完成范围、证据、仍存在的已确认人工工作。 |
| 已完成范围含模拟依赖 | 用户明确把模拟接入纳入本次范围，且真实 Dify 中相应工作流和样例通过。 | 只完成约定范围，不表示真实接口已接通或可直接生产使用。 |
| 已暂停／需处理 | 需要用户决定、补条件，或达到停止条件。 | 原因、已保存进度、下一步选项。 |

特别说明：

- 只在前端展示的模拟运行不能证明 DSL 有效或应用可运行。
- 对原本要求真实接口的需求，采用模拟方案须先确认变更；不能单方面将真实接入从验收中删除。
- 用户允许模拟和人工微调，不等于放弃工作流内部结构、变量及主要逻辑的正确性。
- 第一版不承担客户生产 SLA、业务准确率百分比或所有场景覆盖率的未经约定承诺。

### 6.3 完整交付包

- 目标版本与类型明确的 DSL 文件。
- 实际创建／更新的应用位置，或尚未导入的原因。
- 最终需求说明与范围取舍。
- 流程及具体配置说明，包含关键选择的理由。
- 试跑报告：样例、预期、实际、错误、修复和验证状态。
- 待办与调试指南：模拟位置、待填参数、真实接入和重试步骤。
- 版本、修改和确认记录。
- 若需要外部开发：只交付方案、依赖和接入条件，并标明范围边界。

## 7. 建议实现方案

本节是开发建议，不把框架选型当作用户已确认的业务需求。依赖版本在开始开发时锁定。

### 7.1 整体结构

```text
本机浏览器：对话 + 任务工作台 + 设置
                    |
                    v
本机后台：任务状态、确认、执行、版本与交付
        |               |                |
        v               v                v
模型适配与路由     Dify 专业知识库      确定性工具
        |               |                |
        +---------- Agent 循环 -----------+
                         |
                         v
                 目标 Dify 连接适配器
```

### 7.2 技术选型建议

| 部分 | 建议 | 说明 |
| --- | --- | --- |
| 前端 | React + TypeScript | 复用当前原型布局，接入真实状态和操作。 |
| 聊天组件 | assistant-ui | 复用聊天、附件与消息交互，通过自定义 Runtime 对接后台。 |
| 后台 | Python + FastAPI | 实现本机 API、任务执行及模型／Dify 工具。 |
| 模型适配 | LiteLLM 或同类适配层 | 优先使用库方式；是否需要独立代理服务另行验证。 |
| 本机持久化 | SQLite + 本机文件目录 | 数据库保存任务与版本索引，目录保存材料和成果。 |
| 执行状态更新 | HTTP + 事件流 | 支持聊天输出、执行进度、确认和暂停继续。具体协议在接口设计时定。 |
| DSL 生成 | 结构化流程方案 + 类型／版本适配器 | 模型处理语义，程序生成固定字段、ID、连接及序列化。 |
| 执行控制 | 明确状态转换 + Agent 工具调用 | 确认、上限和状态由程序落实，不能只靠提示词。 |

assistant-ui 提供连接自定义后台的 Runtime 方式：[官方说明](https://www.assistant-ui.com/docs/runtimes/custom/overview)。FastAPI 用于 Python API 后台：[官方文档](https://fastapi.tiangolo.com/)。LiteLLM 提供多服务统一调用能力：[官方文档](https://docs.litellm.ai/docs/)。这些资料支持选型方向，不代替本项目兼容性测试。

### 7.3 Agent 的职责

- 理解需求、追问、设计业务方案。
- 检索与任务相关的节点规则、DSL 示例和版本信息。
- 生成结构化需求、配置、流程、提示词和代码。
- 选择允许的工具，依据真实结果继续处理。
- 解释失败与替代方案，必要时请求用户决定。

### 7.4 程序必须落实的职责

- 需求和确认版本的管理。
- 未准入或未确认时阻止相关执行。
- YAML／图／变量等确定性校验。
- 资源 ID 映射、真实接口调用、结果记录。
- 用量、重试、超时与停止条件。
- 版本保存、测试失效、交付状态计算。
- 模拟与真实执行的标记。

### 7.5 Dify 连接适配器

至少抽象下列能力，并为每个目标环境记录“可用／不可用／待验证”：

1. 读取版本、支持类型及所需资源信息。
2. 查询模型、知识库、插件及节点依赖。
3. 按确认方案准备知识库和文档。
4. 导入 DSL，取得实际应用标识与错误。
5. 获取当前应用／导出的 DSL，保留人工调整。
6. 执行样例、读取运行结果和错误。

导入／管理接口和应用运行接口可能采用不同认证方式。不能默认普通应用 API Key 可完成全部管理操作。实际方式以选定版本、部署条件和授权能力验证为准。

官方资料：[Workflow 与 Chatflow](https://docs.dify.ai/en/cloud/use-dify/build/workflow-chatflow)、[DSL 导入服务源码](https://github.com/langgenius/dify/blob/main/api/services/app_dsl_service.py)、[导入控制器源码](https://github.com/langgenius/dify/blob/main/api/controllers/console/app/app_import.py)。开发时应读取对应版本，不直接依赖持续变化的 main 分支。

### 7.6 多模型与子 Agent 的使用原则

- 开发时：较轻量模型处理独立、可验收的任务；主 Agent 负责设计、整合和最终检查。
- 产品运行时：主 Agent 统一管理用户对话和任务；轻量任务可通过专用模型调用或子 Agent 完成。
- 多模型不等于必须多 Agent；是否拆子 Agent 以任务独立性和收益决定。
- 子任务只接收必要上下文，返回限定结果，避免复制完整历史。
- YAML 检查、图遍历等优先使用程序。
- 记录所有模型、子任务及重试成本，和单模型基线比较。
- 不承诺固定节省比例；低单价可能降低费用，但子 Agent 可能增加总 Token。参见[多 Agent 开销说明](https://developers.openai.com/api/docs/guides/responses-multi-agent)。

## 8. 开发阶段、内容和退出标准

以下是同一目标的逐步实现顺序，不表示永久排除尚未实现的复杂场景。每阶段结束说明实际支持范围和已知限制，不把中间阶段当全量产品完成。

### 阶段 0：环境与连接可行性验证

内容：确定真实 Dify 版本、类型、地址、认证、可用模型／库／插件；配置一个真实模型；验证工具调用等所需能力；验证导入、试跑、读日志、获取最新 DSL 和知识库管理的方式。

交付：环境能力矩阵、连接验证记录、首批类型／节点清单、兼容限制和技术选型。

退出标准：至少一个真实模型可用；一个目标环境的关键操作有实际证据；受限操作有明确原因和经用户认可的处理方案。未验证的能力仍标待验证。

### 阶段 1：本机工作台与持久化基础

内容：正式前端、本机后台、任务管理、模型与环境设置、文件保存、版本结构、事件更新、暂停继续和运行记录。

交付：可启动的本机程序，替代单文件原型；设置中的连接测试调用真实后台。

退出标准：创建、保存、重开、切换任务和设置正常；状态与数据不串任务；进度不依赖页面始终打开。

### 阶段 2：需求访谈与确认机制

内容：真实对话、材料解析、标准说明单、缺失和冲突识别、头脑风暴、参考程度、具体配置与资源操作、确认版本绑定。

交付：可编辑、可追溯的确认方案；程序强制执行准入规则。

退出标准：缺关键信息时继续沟通；未确认不搭建；变更使受影响确认失效；用户可以整体确认或修改部分选项。

### 阶段 3：DSL 生成与本机检查

内容：目标类型／版本规则、结构化流程、节点配置、提示词、代码、图和变量校验、代码样例验证、草稿及交付说明。

交付：可检查的目标 DSL 和错误定位；不可联网时可输出明确标记的待验证成果。

退出标准：正常案例通过本机检查；故意制造的字段、连接和引用错误被定位；保留指定内容；不把静态校验当真实导入。

### 阶段 4：真实资源准备、导入和反馈修复

内容：知识库准备、资源映射、实际导入、验收样例、错误读取、有限自动修复、实际用量、停止和恢复。

交付：第一条真实端到端链路及完整交付包。

退出标准：真实案例完成“需求—确认—生成—导入—试跑—修改—再次试跑—交付”；关键结果可追溯；暂停和投入上限有效。

### 阶段 5：复杂场景与当前版本往返

内容：扩充类型／节点；复杂分支、批量、循环、连续对话、触发与人工参与；不同知识库准备路线；公司／客户环境差异；读取人工修改后的当前版本；兼容测试。

交付：各类场景的能力矩阵、回归样例和版本变化说明。

退出标准：承诺支持的场景有真实测试；不支持的场景可解释和协商；跨环境重新映射资源；人工改动保留。

### 阶段 6：成本优化、使用完善与项目交付

内容：轻量模型分工、上下文裁剪、缓存及用量对比；安装启动说明、错误体验、完整交付包和演示资料。

交付：可复现的安装与使用文档、质量／成本评估、面试演示材料。

退出标准：优化结果有实际数据；质量退化可发现；所有关键验收项完成或明确列出阶段性限制；新环境按说明可启动和复现案例。

## 10. 验收场景清单

| ID | 场景 | 预期行为 |
| --- | --- | --- |
| AT-01 | 用户只给模糊目标 | 追问目标、输入输出和规则；不提前搭建。 |
| AT-02 | 用户不知道分类规则 | 提出规则与例子，确认后采用。 |
| AT-03 | 文档与参考 DSL 冲突 | 指出冲突，确认最终依据。 |
| AT-04 | 参考程度未明确 | 询问借鉴／保留／复现，并记录选择。 |
| AT-05 | 用户所选类型不适合需求 | 说明原因与方案，等待决定，不自动换类型。 |
| AT-06 | 只有原始知识资料 | 检查、提出整理与建库方案，确认后执行可用操作。 |
| AT-07 | 多个知识库可选 | 提出选择及理由，确认具体库。 |
| AT-08 | 资料业务事实矛盾 | 保留来源、请用户裁定，不静默选一份。 |
| AT-09 | 模型简单聊天可用但工具能力不足 | 标记能力不足，提供调整建议，不继续当全能模型使用。 |
| AT-10 | 接口未提供且用户接受模拟 | 显式采用模拟方案，标记位置及真实接入待办。 |
| AT-11 | 未确认配置或资源操作 | 程序阻止执行，显示待确认内容。 |
| AT-12 | DSL 变量引用错误 | 定位并修复，再检查，不删业务分支。 |
| AT-13 | 已导入但关键样例失败 | 标为需修复或阶段成果，不宣称完成。 |
| AT-14 | 批量任务部分失败 | 按已确认策略继续或停止，输出失败项。 |
| AT-15 | 连续对话信息不完整 | 按规则追问，验证上下文行为。 |
| AT-16 | 自动触发或人工审核能力不足 | 说明环境缺口和替代方案，等待确认。 |
| AT-17 | 切换到客户环境 | 重新核对版本、认证和资源映射。 |
| AT-18 | 用户在 Dify 手动修改后继续 | 获取／接收最新版本，保留改动再处理新增要求。 |
| AT-19 | 修改配置或需求 | 相关确认与测试失效，重新确认和试跑。 |
| AT-20 | 执行中暂停并关闭程序 | 保存阶段及结果，恢复后不盲目重复外部操作。 |
| AT-21 | 同一错误反复无进展或到达上限 | 暂停、汇报证据和下一步，不无限重试。 |
| AT-22 | Dify 断开 | 可以生成待验证成果，明确未完成导入和试跑。 |
| AT-23 | 需求需要新建外部系统 | 提出方案及接入条件，不擅自扩大开发范围。 |
| AT-24 | 用户恢复旧版本 | 保存历史，以恢复版本为基础重新确认／验证。 |
| AT-25 | 启用轻量模型分工 | 比较全链路成功率、总用量和费用，计入重试开销。 |

所有“已支持”能力都应有对应实际测试。没有实现的场景显示支持计划或能力缺口，不能仅靠模拟演示计为通过。

## 11. 首条端到端验证案例

建议用客户售后问答作为第一个验证案例，随后扩展合同处理、批量工单和接口驱动流程。案例顺序是实现策略，不缩减总体范围。

前提：用户选择 Chatflow；提供产品和售后资料；指定目标环境；订单接口暂时缺少，用户确认采用模拟。

过程：

1. 确认服务对象、回答范围、开场白、追问、资料来源和无答案行为。
2. 检查资料、处理冲突，确认知识库准备与检索配置。
3. 集中确认具体模型、参数、节点、订单模拟和资源操作。
4. 生成目标版本 DSL 和代码，检查结构、变量和必要路径。
5. 实际导入指定 Dify，验证正常问答、缺少订单号、资料无答案、订单查询等关键样例。
6. 用户提出新增要求，或提供手动改过的 DSL；保留当前版本后修改并重新验证。
7. 交付文件、配置理由、报告和真实订单接口接入指南。

该案例必须明确标注订单依赖仍为模拟。当前前端原型中的成功动画和示意 YAML，不计入这条真实链路的验收。
