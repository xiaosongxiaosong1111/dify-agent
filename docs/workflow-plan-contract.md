# Workflow Plan v1 contract — current rules (Sierra 0.200)

When existing_plan_context is present, its complete saved plan is the edit baseline, even when stale. Compare current requirements/configuration against the supplied matching prior inputs; preserve unrelated node IDs, input declarations, prompts, independent model parameters, retrieval choices and graph branches. A single fallback-text change does not authorize rebuilding the graph or adding a merge node. If preserving the rest is incompatible or the edit scope is uncertain, return error/needs_decision with concrete options. Context is saved task history, not current Dify evidence or approval; never carry old confirmations/runs into the changed revision. This prompt constraint requires review and does not prove automatic semantic preservation. Since 0.246, a structurally valid regenerated plan that differs from an existing saved plan is retained for explicit review rather than automatically replacing it. The UI shows a value-free change summary and offers the existing exact-text candidate-to-unsaved-draft path; reading/loading does not adopt or approve it. Normal validated saving advances the revision and invalidates relevant confirmations. Identical output and initial planning keep their existing behavior.

This is the current contract consumed by the planning model. Linked files provide developer detail; required generation fields are included here. Use the server-generated capability_catalog in the planning context for the current app-type scope. Detailed sections below are chronological: later explicitly bounded extensions supersede older negative scope statements for that same feature only; they do not enable arbitrary combinations. The catalogue describes compiler support, never actual environment readiness, resource availability, execution approval, or business acceptance. Additive to the initial API contract. User-selected app_type remains immutable. Supported plan node types: start, trigger-schedule, llm, question-classifier, parameter-extractor, list-operator, document-extractor, knowledge-retrieval, if-else, code, template-transform, http-request, iteration, loop, variable-aggregator, assigner, human-input, end, answer. Native Agent uses a separate Agent Plan contract. Since 0.31.0 bounded scalar-state loops are supported under loop-contract.md; root Workflow human-input is supported only within its explicit bounded review contract below; nested containers and human-input inside containers remain unsupported. Version 0.12.0 introduced bounded sequential iteration; 0.21.0 adds explicit parallel execution for the same independent-item body subset.

Since 0.65 root and since 0.75 single-level iteration/loop body list-operator processes only declared scalar arrays (array[string]/array[number]/array[boolean]). config contains explicit input_type (Sierra metadata, not native data), variable:[upstreamID,arrayField], filter_by:{enabled:boolean,conditions:[{key:"",comparison_operator,value}]}, order_by:{enabled:boolean,key:"",value:"asc"|"desc"}, extract_by:{enabled:boolean,serial:"1"}, limit:{enabled:boolean,size:0..10000}. All fields required; disabled limit.size=-1 native sentinel is also supported, never enable it. Conditions sequentially AND; supported string ops contains/not contains/start with/end with/is/is not/empty/not empty with literal string values (empty/not empty require ""); number ops =/≠/</>/≥/≤ with finite literal number strings; boolean is/is not with actual bool. No dynamic macros, string in/not in ambiguity, object/file arrays or nested containers. Native order is filter→extract by filtered 1-based position→sort→limit; nth extraction is before sorting, out-of-range on a nonempty array fails, empty input returns empty. Only result array selectors are supported; nullable first_record/last_record are not allowed. Type must match actual upstream declaration, unknown types are not guessed. Actual manual DSL settings/layout are retained, deriving type virtually from explicit declarations; never rebuild whole DSL. See list-operator.md.

Since 0.62 root and since 0.76 single-level explicit iteration/loop DAG parameter-extractor uses explicit query:[upstreamID,stringField], reasoning_mode:"prompt", parameters:[{name,type,description,required,options?}], literal optional instruction and complete optional model. Names are unique 1—64 char Latin identifiers without double-underscore prefix. Types: string/number/boolean and array[string]/array[number]/array[boolean]; required is an explicit boolean, options only for string and unique bounded literal choices. Do not invent default values, dynamic templates, object schemas, file/vision or function-call capability. It inherits the task model; root Chatflow nodes may inherit configured memory, while container nodes never read Chatflow history. Native outputs include parameters plus __is_success:number (1 or 0), __reason (nullable, not reliably string on success), __usage:object. Native node may be SUCCEEDED with __is_success=0 and defaults. Require failure_policy={behavior:"explicit_success_branch",guard_node_id:"CHECK_ID",success_case_id:"OK_CASE"}; extractor has exactly one source edge directly to this IF, whose only case uses AND and exactly one condition {variable_selector:["EXTRACT_ID","__is_success"],varType:"number",comparison_operator:"=",value:"1"}. IF has explicit success/false edges. Business parameter references must be on paths dominated by the success target, not on failure/common paths; merge success/failure response values explicitly. Additional nonempty/format/semantic checks go in the success path. Model extraction success does not prove business truth. Since 0.63 literal root native extractor edits are preserved under the same actual gate/model/standard memory checks, never patched or regenerated silently. Container extraction requires an explicit DAG and does not read Chatflow history; nested extraction is not adapted; explain unsupported conditions, never remove the failure gate to make validation pass.

question-classifier is supported at the root and inside explicit single-level iteration/loop body DAGs. config requires query_variable_selector (an explicit upstream string source), classes (2—20 unique literal {id,name,label?} items in preserved order), unmatched_policy={behavior:"first_class",class_id:"FIRST_CLASS_ID"}, optional literal instruction and optional model (same complete model contract as LLM). Each class id needs exactly one explicit edge source_handle/sourceHandle; do not invent a false/default branch or silently omit a class. Outputs are class_id/class_name/class_label (string) and usage (object), not confidence or finish_reason. If label is empty Dify uses ClassN. Recommend an explicit other/clarify category first, but the user decides. Classification inherits configured task model and Chatflow memory unless a complete independent model is supplied. This invokes a model and may add cost. Since 0.61 top-level literal classifier native edits/standard bounded Chatflow memory are preserved with explicit merge confirmation. ## Sequential iteration (0.12.0)

This is Dify's iteration container, not a directed cycle or a scheduled batch job. Workflow and Chatflow are supported; never change the selected application type. Array inputs are not adapted: accept JSON array text and use a code node to parse/validate it into an explicitly typed array. Ask the user about batch size, item rules, sequential/parallel mode, explicit concurrency, independent-item and side-effect conditions, output form, failure behavior and cost before treating a business proposal as confirmed. Do not invent defaults for missing business rules. Return `error` if required nested/branch/continue-on-failure behavior is outside this scope or parallel independence is unconfirmed; do not substitute fail-fast or sequential work without agreement.

All iteration config fields are explicit:

```json
{
  "id": "batch", "type": "iteration", "title": "按原顺序处理",
  "config": {
    "iterator_selector": ["parse", "items"],
    "iterator_input_type": "array[string]",
    "output_selector": ["clean", "result"],
    "output_type": "array[string]",
    "is_parallel": false,
    "error_handle_mode": "terminated",
    "flatten_output": false,
    "nodes": [{"id":"clean","type":"code","config":{
      "code_language":"python3",
      "code":"def main(item: str) -> dict:\n    return {\"result\": item.strip().upper()}\n",
      "variables":[{"variable":"item","value_selector":["batch","item"]}],
      "outputs":{"result":{"type":"string","children":null}}
    }}]
  }
}
```

- `iterator_selector` must reference a strict upstream array declared by a code node or previous iteration. Supported input types: `array[string]`, `array[number]`, `array[object]`; declared type must match the producer. No guessing the type of model text.
- `nodes` is an ordered list of 1–12 code, template-transform, llm, list-operator, knowledge-retrieval or declared GET/HEAD http-request nodes in sequential mode. With both entry_node_id and edges, the explicit body DAG also supports if-else, ungrouped variable-aggregator, question-classifier and parameter-extractor. Compiler creates the native iteration-start; do not place inner start/end nodes in IR. No nested containers, document extraction or human input inside the body. Unknown container/body config fields are rejected, not silently dropped.
- All outer and inner IDs must be globally unique and contain only letters, digits, underscores or hyphens. Names formed from container ID + `__iteration_start`, `__scope_input`, `__scope_end` are reserved.
- Inner variables may reference `[container_id,"item"]`, `[container_id,"index"]` (zero-based number), previous body nodes, or outer nodes available on **every** path into the container. No self, future, sibling branch or outside reads of inner outputs. Template variable `value_type` must match the source (e.g. index = number).
- `output_selector` must be a string/number/object output of the last body node. `output_type` must be exactly its array type. Flat ordered results preserve input order, duplicates and empty input. No array flattening. Optional per-item metadata should be generated by an object-producing body code node after discussing the user's output needs.
- Execution is explicit: legacy sequential config uses `is_parallel=false`, optionally `parallel_nums=1`, without parallel declaration fields. Parallel config requires `is_parallel=true`, integer `parallel_nums` from 2 to 10, `parallel_safe=true`, and a nonempty `parallel_reason` (at most 2000 characters) grounded in confirmed requirements explaining item independence, absence of order-dependent shared state, and side-effect conditions. These Sierra declaration fields are not native Dify fields and are never emitted into node data. They are a user-review requirement, not proof of safe code. Never infer concurrency or silently change sequential work to parallel.
- In both modes, `error_handle_mode="terminated"`: failure fails the entire container/workflow; it is not an accepted partial result. In parallel mode dispatched items may still be running when another item fails; do not promise immediate cancellation or zero additional cost. Output is collected by original input index, not completion order. No skipping, automatic runtime repair, retry of the entire batch, or continuation from a stored item checkpoint. Graph validation is not proof that arbitrary generated code respects these business rules.
- Inner LLM uses its explicit full config.model or inherits the task's actual provider/model/completion settings, once per item; it does **not** read Chatflow history. Explicitly bind any required context in its prompt. Model availability gates include nested LLM. Full-task monetary hard stops are not implemented; disclose before confirming model batch workloads.
- Native nodes are flattened into the Dify graph with `parentId`, `iteration_id`, `isInIteration`, `start_node_id` and scoped edges. Emit DSL 0.7.0 targeting Dify 1.17.1. Do not emit an inner end node.
- Single-level iteration DSL can be preserved under the current native scope, type, branch and output checks. Parallel preservation requires an explicit current-file independence declaration; sequential/parallel mode and concurrency are never silently changed. Nested or continue-on-error variants remain unsupported; never drop inner nodes to pass a merge.

## Container scalar-array operations (0.75)
