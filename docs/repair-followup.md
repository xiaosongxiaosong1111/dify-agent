# 修复后验证与原失败输入准备

0.57.0 在已采纳的本机修复记录中增加验证进度及“准备原失败输入（替换输入，不运行）”。用户不再需要手工从旧记录复制重现输入，仍由用户主动确认并点击实际试跑。

## 使用流程

采纳修复后打开原失败记录中的修复工作台。验证区按当前保存状态提示：待确认配置、待构建、待导入、待重跑、结果未知、重现仍未通过、待核对新轨迹、待重跑现有样例、本次修复检查通过或模拟阶段通过。可以主动刷新，不自动派发 Dify 或模型请求。

准备输入只填试跑区，正式样例主动选回同一 case_id，保持输入、预期及后续轮次；自由试跑只填原输入，不自动变成正式样例。缺输入、原样例已变化、需要旧会话历史、疑似凭据或来源失效均说明条件，不补空值或假装完整重现。原会话不复制、不回退，须整理为新会话开始的正式多轮样例。

## 判定标准

采纳时冻结修复后需求、配置、流程、样例、应用类型和环境的契约哈希，原失败记录哈希及所选对话轮次。当前修订、内容或原失败证据变化，验证计划只作历史参考。0.56 旧记录缺少契约时不补造凭据或证据，明确请人工核对。

只使用当前修订、App、类型和环境绑定的运行。按严格 JSON 比较原输入及样例快照，True 与 1 不等同，改变预期不能替换原失败重现。按当前实际输出重新执行已有规则，而非信任旧 evaluation.status。正式人工判断仍由已有人工复核流程处理。

原错误消失需要原失败输入的新运行通过，且最新诊断的运行哈希、采集修订、App、对话轮次、执行／发布／成果图都一致；每个修复节点有明确 succeeded 且无错误的实际轨迹。缺节点、截断、旧报告、不同轮次、节点失败或发布图不同均不计错误消失。

目前尚未实现可靠的受影响样例剪枝，因此列出全部现有样例供重新核对；没有正式样例，即使自由重现和节点成功，也提示补齐，不标完整验证。含模拟依赖只记阶段通过；最终判断不修改原运行、任务验收或交付等级。未知结果先核对远端，不自动重跑。多轮失败处于非最后轮时，现有诊断可能缺少该轮成功轨迹，须人工核对，不能拿最后轮成功代替。

## API 与验证

- `GET /api/tasks/{id}/runtime-repairs/{repair_id}/verification`：只读汇总阶段、重现状态、样例待办、错误消失证据及准备条件，不返回原输入／输出。
- `POST /api/tasks/{id}/runtime-repairs/{repair_id}/prepare-input`：revision；重新核对来源后返回 input／case_id，只准备，不修改任务或发起运行。

新增 28 项隔离检查。最近完整后台 1548 项通过，随后补充的对话轮次一致检查及相关 28 项通过；没有把未整套重新采集的新增项计入完整数字。浏览器修复工作台 8 项受控检查、构建及视觉检查通过，三项写入只在内存拦截，真实任务未变；没有真实 Dify 应用创建、真实修复后执行或付费模型调用。
