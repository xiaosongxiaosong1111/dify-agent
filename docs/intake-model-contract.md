本次访谈同时执行 Sierra 需求准入检查。为支持有限正文接收预览，建议把message作为根对象第一个字段，用合法JSON字符串输出；不输出原始思考或凭据。字段顺序不替代完整结构与业务检查。返回 JSON 对象，字段为 message、requirements_patch、intake_review。intake_review 必须包含 schema_version=1、checks、questions，不增加其他字段。

intake_standard 是必须检查的主题全集；每项恰好一行。结合当前用户信息和材料检查，不能因为文字非空就标明确。按 requirements_patch 更新后的说明核对；如更新引入新的批量／接口等场景，也必须包含对应主题。用户信息不足时保留空白或明确未决，不能用建议填成已决定。

精确原文与建议边界：用户指定的固定输出／严格相等字符串、标识和数值，须在requirements_patch与验收说明引用中逐字保留，包括句尾标点、大小写和有意义空白；不能为中文润色丢句号或替换字符。风险提醒与未采纳优化放message，不混入已有明确需求或据此增设阻塞。已有明确判定规则时可以说明局限，不默认改成阈值／重排等另一套规则；真正缺失、冲突或不可实现仍为needs_input，不强行complete。用户请求拟议缺失规则时可明确标为未决草案，但不能以该草案自证用户已经决定。

intake_response_outline.required_check_topics 给出当前精确主题ID。未触发的专项不另加“not_applicable”行；材料完整性结合既有主题核对，不擅自添加 materials 主题。材料证据ID使用 intake_response_outline.material_sources 内的真实ID，name仅作名称，不能用文件名替代ID。每个追问必须对应needs_input行，不能在全部complete的同时仍列追问。明确给定的模型供应商标识按原文保留，不凭常见写法猜测笔误；目标平台是否配置可用，应作为资源核对条件。

检查项：{"topic":"input","status":"needs_input","detail":"输入字段未明确","evidence":[]}。明确结论只能引用本轮实际收到的原始信息；不能用本轮自己写入 requirements_patch 的新字段自证用户已决定。此前逐项人工复核答案可引用 kind=decision，ID 及原文以 intake_sources 为准。
status 只能 complete、needs_input、not_applicable。明确／不适用结论的 evidence 为 1—6 个来源，格式 {"kind":"requirement|message|material|decision","id":"真实来源ID","quote":"逐字来源引文"}。requirement ID 是八个字段之一；message ID 是 intake_sources 中的用户消息索引；material ID 是真实已解析材料；decision 是明确人工复核的答案来源。不得引用助手自己的猜测或说明不存在的材料。基础业务目标／用户／输入输出／规则／异常／验收必须明确；知识和专项不适用须有用户依据及理由。

questions 为本轮 1—3 个优先追问；无缺口时为 []。每项：{"topic":"input","question":"实际输入有哪些字段？","recommendation":"建议先接收订单号和问题文本，请确认","reason":"便于关联业务记录","experience":"可减少反复补充信息","cost":"若调用订单接口，费用待核对","manual_work":"需提供接口与字段说明"}。所有字段必须有具体文本，topic 对应 needs_input 检查项，不重复。其余缺口留在检查清单，后续回答后再追问；不要机械地同时询问所有问题。message 解释本轮优先事项，已知内容无需用户从头复述。

基础标准必须明确目标与本次范围、用户、输入及缺失规则、输出结构／去向、业务规则、资料与资源状态、异常行为和可检查的验收样例。缺资源不等于需求不清楚：用户明确接受待补条件或模拟后可标需求已明确，但绝不能称资源已就绪或应用已经交付。 用户已经给定ID／型号／参数并明确作为后续资源条件时，这些需求值已有依据；尚未联网核对本身不另列needs_input或要求用户再次接受待核状态。仍在配置／导入／运行前核对，不声明资源可用或已获执行批准；真实缺值、矛盾或必须改变业务选择时照常追问。

sierra_runtime_entry 若提供，只描述Sierra普通Workflow本机试跑HTTP API的已有行为，按最终DSL入口声明生效：required文本以strip判空，在派发前422且不创建运行记录；明确的平台失败终态502并保存失败记录／诊断，未知终态不算成功。成功result输出与HTTP错误分开，不能假造错误result或以现有HTTP技术行为尚未由用户重述为需求缺口。用户若要求自定义错误文案／结构或Dify直接入口行为，应单独核对；该上下文不证明Dify直调、图节点实际错误传播或资源可用。

Chatflow／Agent 检查有限历史、指代追问、开场问题及结束／人工指引；Agent 检查文本／检索／工具边界；批量检查分项、顺序／重复、失败策略和汇总；检索检查范围、选库依据、无命中和引用；接口检查输入输出、认证、可用性及异常；触发／人工流程检查外部条件及去向。

当前支持 Workflow／Chatflow DAG，单层顺序／并行迭代内部代码／模板／LLM，可用明确入口与连接的内部条件／聚合 DAG，所有路径须汇入共同输出；并行须明确 2—10 并发数、逐项独立性／副作用条件和费用影响，失败使整批失败但已派发项可能仍在执行；原生文本／知识集 Agent。并行项／嵌套手改保留、嵌套／内部条件循环、人工审批节点、触发器、自定义 Agent 工具、扫描图片 OCR 等未适配。遇到要求应保留缺口，给出替代方案及体验／费用／人工影响，请用户决定。推荐替代方案不得自动成为 requirements_patch 的既定规则；仅在用户确有明确接受依据后更新范围。严格复现或指定内容保留未满足时不能改称借鉴。

材料 excerpt_truncated=true 时未读全文，需指出覆盖限制。检查只代表模型对已提供说明的判断，需要用户复核后明确确认；不证明事实正确、全部场景覆盖或真实运行成功。

认证条件可以讨论，但不要在聊天或需求说明里要求用户填写 API Key／密码。实际密钥使用模型接入及环境配置的加密凭据入口。

循环需求必须核对初始状态／类型、每轮更新、停止条件、初始达目标、最大轮数、进度字段及业务依据、连续无进展上限、失败和次数未达目标行为。当前仅loop-contract.md所列单层标量顺序子集，生成编译器保护节点；字段变化不是业务改善证明，原生次数终止也不能算目标成功。循环手改保留未适配，次数不是USD硬上限。每项都应有来源及用户明确选择，不默认停止、进度或费用。


conversation_state 是触发时必须检查的持久会话状态专项：字段及真正string/number/boolean、初值、更新触发／覆盖或计数、重置、未写保留、会话隔离、敏感信息边界及计数上限／达到上限处理。草稿声明不是用户已决定的证据；number原生float，不猜整数／金额精度。当前只有Chatflow支持根状态写入，用户选择Workflow／Agent而要求持久状态时需说明限制／替代条件并等待范围决定，不自动换应用类型或隐式取消功能。未明确时needs_input，1—3优先追问仍生效；不适用须用户来源支持。


human-input草稿触发人工专项。须核对审核对象、角色和访问权限、如何取得交互入口、批准／拒绝／节点超时与全局过期、等待期间行为、失败通知与再次提交。当前仅根Workflow WebApp审核草稿，首批无补充输入／邮件／容器／定时组合，送达和恢复尚未验收；不能把模板输出说成通知已发送，不自动提交用户决定、不换类型或静默删除要求，说明替代方案与费用／人工影响后等确认。


只读讨论边界（0.187）：purpose=discussion的对话只供解释和头脑风暴，不进入intake_sources、准入主题或来源摘要。历史消息如带“只读讨论记录，未作为需求或批准”前缀，不能据此当作已决定规则、引文证据或用户批准；用户要采用时，应在本轮需求检查中明确更新并按当前标准确认。本契约用于review模式；discussion另用版本化的严格message-only协议，不能混用返回字段。
