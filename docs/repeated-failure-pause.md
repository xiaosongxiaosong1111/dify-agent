# 重复运行失败暂停（0.64）

同一任务在同一环境、相同完整输入及样例下，连续两次可信失败的节点 ID、节点类型和保存错误摘要完全相同，暂停该输入继续试跑，以及最近这次运行的模型代码修复请求。历史跨修订、跨本任务新建的 App 保留，不能靠新版本清空计数。其他输入或不同样例不算重现；成功、未知、缺失或不可信证据会中断该输入的比较链。

这是一条确定性保护，不是对“业务没有进展”的语义判断。错误摘要不同也不证明修复成功。已有会话、多轮样例、部分轮次诊断、脱敏或截断的错误不参与比较，不能据此宣称问题已排除。

每条失败必须有最新、完整、当前来源的保存诊断：源运行哈希未变、采集修订等于当时运行修订，执行／当时发布／当时成果核心图一致。比较链最后一条还必须属于当前修订和 App，成果图仍一致。后台只用本机保存信息，不额外读取远端、不向模型发送输入或错误。页面不回显输入、错误正文或比较哈希的原文。

运行页的“重复失败暂停”集中展示记录和节点，推荐先补条件或修改方案。用户也可说明原因并明确确认只开放一次试跑，或者一次模型候选请求，二者选一。保存决定不派发请求；仍需全部现有需求、配置、资源、数据出站与费用门禁。模型候选仍须独立核对与采纳。选择修改方案保留暂停，不删除失败记录。

一次许可绑定修订、完整失败链及核心图，实际启动前在 Store 锁内消费。失败、派发前后中断也不自动恢复许可；若未实际派发需人工核对，不声称没有费用。旧证据的一次许可已消费后，不能再次授权；重复读取相同诊断（新 ID／时间）不会刷新许可。出现新的相同失败，重新暂停并要求重新决定。服务重启保留决定，不重放操作。

接口：GET `/api/tasks/{id}/failure-watch`，POST `/api/tasks/{id}/failure-watch/decision`。决定的原因和审计记录在独立本机存储中，不修改业务修订、不覆盖手改或凭据。凭据文本拒绝且不回显。

开发验证采用隔离 Task、替身模型和替身操作，不创建真实 Dify 应用、不触发付费供应商。实际 Dify 修复闭环仍待具体资源方案授权后联调，不能把本机检查当成真实交付验收。

0.70起交付报告同时记录当前执行阈值、重复失败及一次许可使用状态，审计超500条明确截断及总数；不复制处理原因全文或原重现输入，不产生新的资源许可或业务验收结论。
