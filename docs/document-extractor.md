# HTTP文件文档提取（0.71）

首条支持路线为：原生HTTP获取文件，document-extractor提取文字数组，再进行数组处理、模板展示或逐份迭代。Sierra生成／编辑／保留该路线，构建不发起HTTP、文件下载、解析服务或模型请求。

首批仅接受全路径上游的HTTP.files（array[file]）；普通URL、HTTP.body文字、代码拼成的文件对象、用户上传入口、单文件和容器内部暂未适配。配置必须明确variable_selector=[HTTP节点ID,files]、input_type=array[file]、empty_policy=return_empty_array。后两项是Sierra的明确声明；不会伪造成原生解析参数。导出is_array_file=true用于Dify编辑器正确显示数组输出，原生后端实际类型仍由文件输入决定；实际手改缺失／冲突标记不能静默保留为文字或自动纠正。

原生text输出是按文件顺序排列的array[string]。空文件列表返回空文字数组，非空文件的提取内容也可能为空；这不证明业务已成功。不能直接作要求string的问题来源。需要无文件追问、空文字拒绝或坏文件逐项汇总时，先确认业务分支；本节点不会自动跳过坏文件或编造默认文字。

原生优先用扩展名，再用MIME选择解析器。扫描PDF不提供OCR；DOC/XLS等格式可能使用目标Dify配置的Unstructured服务发送文件，并增加费用。需求准入会主动询问文件获取、格式与权限、空／扫描／坏文件行为、解析环境／数据出站／费用及人工替代。没有具备这些条件时应说明可提供文字版、明确解析服务或缩小范围的体验和人工影响，由用户决定；不额外开发转换服务。当前仍不能保证编码、表格、排版或完整文字原样保留。

流程页有文件来源选择、完整selector JSON及空输入方案按钮，所有动作仅写未确认草稿，不默选来源、插入分支、关闭认证或上传文件。实际原文件中的选择和布局可经三方合并、确认与构建保留，不整份重编译。最终语义摘要只新增文件来源引用，不发送文档内容；轻量范围升级9，旧8必须重新确认，不自动换主模型。

错误诊断区分解析服务、格式不支持及下载依赖；可信当前来源可定位文档卡，不能误导修改搭建助手的模型Key。不修改运行／验收、不自动下载或重试。

开发证据：隔离生成与Workflow／Chatflow实际文件往返、类型／来源误用拒绝、新准入及旧范围拒绝；原生DTO、纯内存空输入／错误类型及纯文字／JSON解析核对通过，没有HTTP或模型调用、应用创建或完整工作流执行。真实文件获取、解析及业务整图仍需具体资源方案批准后验证，不能把开发检查计为实际交付成功。
