# 定时需求专项准入（0.118，已部署）

当用户描述定时／定期执行／scheduled，或每日、每周等自动执行需求，或者草稿包含trigger-schedule时，需求标准加入三个独立专项，随实际访谈或人工复核显示。

1. 时间规则：是否确实自动启动、时区、频次、时间、周几、月日／月末、短月、错过是否补跑及夏令时。明确当前仅Workflow visual UTC／Asia/Shanghai适配，不能自行换类型／时区。
2. 输入与送达：每次输入来源、输出收件人和获取方式、空数据、重复派发、上一轮未结束、并发与去重／幂等。需要已有存储或通知接口时说明权限和模拟条件，模板输出不等于已发送。
3. 运营与成本：持续周期和启停责任、失败通知、重试与无进展上限、每次／累计费用、监控和超限处置。试跑预算不约束平台后续调度，无自动到期停用，停用不取消队列；能力缺口与替代方案必须先说明并确认。

新专项改变准入上下文，已有旧复核不能自动升级为完成；模型检查须逐项覆盖当前标准、引用真实需求来源，草稿不能证明业务政策已由用户确认。人工逐项回答持久保存，标为用户声明，不冒充模型验证；保存不会自动确认需求、配置、发布或运行。

普通文本处理以及单独Webhook需求不会机械增加三个定时专项。Chatflow／Agent可以提出定时需求并讨论条件，但类型仍由用户决定；专项访谈不意味着平台已支持该类型的定时节点。

实际证据：11新增专项、98相关通过10.23秒、启用准入31相关通过6.34秒，最终专项11通过1.40秒；完整2361通过150.76秒。4动态页面/视觉通过，真实API写0/原Task不变，前端同0.117构建，无实际模型/Dify调用。
