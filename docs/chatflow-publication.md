# Chatflow首次发布入口（0.275）

此前Chatflow只能导入和试跑，Sierra的首次发布卡片只适配Workflow，用户须到Dify另行处理。现在Chatflow运行页也可明确核对并首次发布当前新建导入App，不改变用户选择的类型。

协议依据为固定[Dify1.17.1发布控制器](https://github.com/langgenius/dify/blob/1.17.1/api/controllers/console/app/workflow.py#L1193-L1256)：同一发布资源接受advanced-chat和workflow。使用固定tag核对，没有依赖main分支或访问本机Dify来探测接口。

## 使用与边界

1. 当前修订需求、配置及成果须已确认，并有同环境/修订/App的成功新建导入依据；成果及导入基线的app.mode须为advanced-chat。
2. 在运行页点击“读取草稿并准备发布”。先核对远程App ID和类型，再读取原生草稿和发布状态；仅匹配且尚未发布时提供15分钟有效的确认。
3. 核对页面中的Chatflow类型、目标App、修订、环境及成果摘要，勾选后明确确认。确认前重新核对，最多派发一次发布，再读回发布图匹配后保存回执。

完整节点data/边/环境和会话变量/features均参与图匹配，记忆配置位于节点data中，开场白/建议问题也保留。确认之后的外部修改、App身份/类型不符、已有发布或原生hash变化均拒绝；不覆盖已发布应用，不自动创建Key或试跑。最终发布返回期间本机类型、修订或环境改变，也不标当前版本成功。

发布前持久记录派发意图；可能已经派发的异常、401/超时、发布图不匹配均保持unknown，刷新和重启不重发。前端及报告只认匹配应用类型的成功回执；在途/未知记录即使尚无result字段也继续阻止重发，不误显示为“还未发布”。Workflow旧成功记录缺省类型保持兼容；缺少类型绑定的旧就绪提案不能直接确认，须重新核对，不迁移或篡改成功/失败历史。

Chatflow常规准备3次管理读取（App身份、草稿、发布状态），确认4次读取及最多1次发布POST，合计7读/1写；认证可能增加请求，不是计费或请求硬封顶。旧Workflow常规5读保持。原生Agent、自动触发及人审专用资源不扩展到本入口。平台没有草稿条件锁这一既有边界继续披露，事后读图不能抹去已经发生的发布。
