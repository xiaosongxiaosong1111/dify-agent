# 顺序批量处理：实现范围与验证

当前更新：0.21.0 新增单层并行模式，严格并发数与独立性声明、实际策略展示、原生实体解析和受控检查已通过；真实应用未执行。下文为 0.12.0 顺序首版的历史边界，最新见 [并行迭代说明](parallel-iteration.md)。旧真实联调审批没有因此自动获得批准。

更新：2026-10-10；Sierra 0.12.0；目标 Dify 1.17.1，DSL 0.7.0。

## 已实现

- Workflow／Chatflow 的单层顺序 iteration 容器，内部 1—12 个按顺序执行的代码、模板或大模型节点。
- 输入数组来自上游明确类型的代码输出或前一迭代输出：array[string]、array[number]、array[object]。开始输入仍为文本；JSON 数组文本先由代码解析。
- item、从 0 起的 index、前面的内部节点以及所有路径可用的外部上游变量。全局 ID、作用域、输入／汇总类型、模板绑定类型和代码语法校验；拒绝自身尚未生成的值与内部值向外泄漏。
- 固定并明确确认顺序、terminated 和 flatten_output=false。输出为最后内部节点 string／number／object 的数组。某项失败时整批失败，不把部分结果计通过。
- 原生 iteration-start、parentId、iteration_id、内部边与容器布局；外部节点按容器宽度避让。
- 内部 LLM 使用任务所选模型和参数、逐项调用，不读取 Chatflow 历史；模型缺失会阻止确认与构建。内部代码的有限语法修复保留容器策略、连接、资源和关键代码内容。
- 流程页的“填入批量处理样例”，仅填本地草稿；最多 100 个字符串、JSON 类型校验、去空白并转大写是该示例的具体规则，不是对所有任意计划施加的运行数量上限。
- 摘要展示实际策略、输入／输出类型、内部步骤及历史／费用限制。未适配或未填写的策略明确标注；样例仍需检查、保存和确认。

## 明确未完成

并行、内部条件分支、嵌套迭代、一般循环、内部检索／HTTP、继续或跳过失败、从中间项恢复、运行时自动修复和全任务费用硬上限。原生 Agent 使用独立契约，不因 Workflow 新增 iteration 获得批量能力。

含 iteration 的最终 DSL 三方保留尚未适配：可以读取、保存参考，合并验证／构建会明确阻止，不会删除内部节点来通过。静态 schema 不能证明任意生成的代码符合业务需求。

## 等待批准的真实联调

自动审批审查拒绝了 `work/iteration-live.py` 的执行，理由为具体资源方案和持久化外部写入尚缺用户明确批准。脚本尚未执行，不能把计划中的真实步骤写为通过。

具体方案：使用已有 DeepSeek 执行一个受当前时间、重试、费用估算上限约束的规划任务；生成虚构技术 Workflow。随后只在本机 Dify 新建、发布 **1 个独立测试应用**，生成仅该应用的运行 Key，执行 4 个正常代码样例（顺序、重复项、空数组、空白项）和 1 个故意中途失败样例。应用不调用模型、接口或知识库；不覆盖既有应用。真实规划的用量与费用估算、Dify 实际输出、失败诊断均保留；未知写入不自动重试。测试应用与 Key 持久存在，不自动删除。

用户批准后再执行、记录实际结果；故意失败保留为失败记录，不能冒充必选样例通过。完整客户业务、内部 LLM／模板／数字／对象数组的 Dify 实际运行仍需扩大验证。
