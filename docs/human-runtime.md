# 人工运行资源与等待表单（0.122，已部署）

这一批实现专用的“准备具体资源方案 → 人工批准资源 → 一次创建／发布／生成Key／运行 → 采集等待表单”链路。通用导入／试跑仍拒绝人工节点，避免绕过独立资源方案。T116没有整体完成：0.123已补[独立人工提交与恢复证据](human-decision.md)，强制审核人身份、其它送达渠道、完整业务和真实平台验收尚缺。

## 明确支持范围

最终成果必须是Dify 1.17.1 Workflow，唯一Start和唯一根human-input；其它节点仅无变量、无表达式的固定文字template-transform与end。开始输入只接已声明文字／选项，审核引用只接二段文字来源。模型、知识库、HTTP、代码、文件、通知、容器、定时、多审核、额外特性或环境／会话／管道变量明确拒绝，不删除后生成。

开始输入核对必填、选项、长度和未声明字段。原文字preflight保留兼容行为，人工方案使用完整form_schema／check_values，不依赖它忽略纯文字的旧逻辑。审核对象采用文字替换，不执行Jinja。当前环境与主模型已保存凭据、常见密钥形式不能进入出站DSL或输入；该检查不声称识别所有未知秘密。

## 具体批准与执行

准备只读本机成果，保存修订、原字节SHA256、核心图摘要、目标环境、完整出站DSL、输入、动作／交互／等待和资源哈希。方案预计一个新App、一次发布、一个新App专属Key、一次Workflow运行及一个等待表单，人工提交次数为零。最多4次平台只读核对，总处理180秒、SSE采集80秒；失败不重试或删除遗留资源，宿主费用不能保证为零，指定审核人权限未强制限制。

用户明确接受具体方案后，执行API核对当前修订、确认、准入、最终成果和原环境；冻结原管理／CSRF凭据并在每一步前后核对。仅导入新应用，不传已有App ID。导入要求明确completed，不自行接受兼容警告。发布前写检查点，核对实际发布UUID、完整核心图、特性及环境／会话变量；缺失、原生默认补充或秘密遮罩不猜作相等。新Key只用于该独立应用，不替换原环境Key。

四项写入均先持久保存单次尝试。处理中、等待或未知的任务不能另建一套人工资源；旧方案不能重放。中断恢复只保存unknown，已知App／Run保留，不自动重复任何写入。尚无可信Run ID的未知写入需人工核对，不能猜测资源或自动清理。

## 表单与读取

原生SSE核对workflow_started的发布UUID和运行ID，human_input_required的原Run／Node／Form、两个已确认动作、空输入、WebApp可见、无其它审批渠道、有限到期时间和精确渲染正文；workflow_paused须仅等待原审核节点。最多500事件、2MB流量、100KB单事件；不保存节点原始输入／输出、暂停原因或错误原文，不遇到未知事件后省略再计完成。

等待表单采纳前，主动核对原运行详情的可信ID、paused状态和完整实际执行核心图。App运行Key和表单token在后端专属owner加密秘密表中保存；任务、公开资源记录、DSL、页面和浏览器存储不包含令牌。审核正文作为需要人工查看的对象保存和显示为纯文本，不是HTML或自动执行指令。

页面可以主动读原运行状态，目标绑定原记录，凭据和记录改变时不保存旧读取。只读看到终态仅记platform_finished，不能推断是谁提交、是否接受了本次决定、是否正确恢复或业务通过；不自动评价样例。平台日志、默认值、输出和错误正文不回传。本批仅等待，0.123另有独立具体动作确认／单次提交和只读恢复证据；没有取消或盲目新run按钮。

这些证据使用临时Store、MockTransport和拦截页面请求，不是实际Dify创建表单／提交／恢复／权限或客户验收。没有新增真实Dify资源或付费模型调用。
