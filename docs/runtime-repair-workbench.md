# 运行失败后的本机修复工作台

0.56.0 将运行诊断接到修复候选、差异查看、主动采纳、新修订确认和重新构建。原 T095、T096 仅有规划修复及诊断的部分，现在新增运行失败证据驱动的首批本机修复规则；完整自动修复和真实修复后试跑验收尚未完成。

## 如何使用

1. 在运行页打开明确失败的 Workflow／Chatflow 记录，读取 Dify 节点轨迹和当前发布来源。
2. 来源匹配且轨迹完整时，点击“生成修复候选并查看差异”。Sierra 从已保存诊断检查当前计划，生成独立候选，不改正式任务、不调用模型、不请求 Dify。
3. 展开节点查看原代码与候选、静态检查提示。首批仅支持明确 `NameError: name 'math'/'re' is not defined`，代码中此名称未绑定且仅通过属性使用，补一行 `import math`／`import re`。
4. 点击“采纳为新修订，重新确认配置”。旧版本和失败记录保留，配置确认、成果及应用绑定失效；需重新确认配置并构建，另按具体资源方案导入、试跑。不会覆盖现有 Dify 应用。
5. 重开页面可查看独立保存的候选及采纳记录。旧修订候选只能参考，不能套用旧诊断或把失败记录升级为通过。

## 修复边界

规则只用 AST 和符号表检查代码，不在宿主机执行。任何作用域已经赋值、导入、声明 global／nonlocal 或用作参数，名称直接作为值而非模块属性，多个不同错误、混合失败节点、语法错误、未知代码语言均不猜。插入保留模块文档、future 导入、原注释及 CRLF；去掉新增导入后的 AST 必须与原代码完全一致。重复的同一节点同一错误只生成一项改动。

Dify 1.17.1 的原生 `api/core/helper/code_executor/python3/python3_transformer.py` 在执行用户 `main` 前导入 json，因此普通 main 漏 json 导入不作为首批规则或真实错误案例。math／re 的候选是否能在用户实际 Sandbox 中执行仍需真实试跑，静态通过不保证运行成功。

后端每次预览和采纳核对任务修订、当前 App／环境、运行内容和复核哈希、最新诊断、采集修订、远端 failed、完整轨迹、执行／发布／当前成果的图指纹、计划重新编译后的图及完整来源签名。结果未知、待执行操作、手改 DSL 保留路线、来源不同均拒绝。采纳时重新生成并比较候选，防止直接修改候选记录后采纳。

这里的来源只证明采集时核心图一致，不能证明远端发布后持续没有变化；采纳仅更新本机方案，不自动修改任何远端应用。凭据、客户全文和错误原文不发送供应商；候选需通过既有本机草稿凭据检查。

## 接口

- `GET /api/tasks/{id}/runtime-repairs`：本任务持久候选和采纳记录。
- `POST /api/tasks/{id}/runs/{run_id}/repair-preview`：`revision`、最新 `diagnostic_id`；相同来源重复请求返回同一候选。
- `POST /api/tasks/{id}/runtime-repairs/{repair_id}/apply`：`revision`；从后端记录取候选，不接受任意计划；返回新任务和已采纳记录。

候选／任务通过同一 SQLite 事务采纳；旧版本先留存，重复或并发采纳不能产生第二个新修订。配置和样例仍使用既有修订门禁，不继承旧验证通过。

## 验证及剩余范围

28 项新增本机检查覆盖修复—差异—采纳—确认—构建链路、来源变化、重复及混合失败、凭据保护、重启保存、候选篡改和跨任务隔离。5 项浏览器检查使用受控任务，写入只拦截到内存，真实用户任务不变。前端构建及视觉核对通过；最终完整后台 1521 项通过，既有 Starlette 提示 1。当前源码和运行均 0.56.0。

本次未创建 Dify 应用、未执行实际修复后工作流、未调用付费供应商。缺资源、输出类型、变量来源、HTTP 数据展开、模型提示词及业务错误没有自动修复规则；不计为全量 T095／T096 完成。
