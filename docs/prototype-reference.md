# 原型参考与实现对照

日期：2026-10-09。需求依据：[需求规格 v1.0](requirements-v1.0.md)。

## 1. 原型的作用

[交互原型](../reference/prototype.html)是布局和操作流程的暂定参考。用户已同意暂用该方向，正式实现允许根据测试调整细节，但不能悄悄改变需求和验收标准。

原型不连接模型或 Dify，回复是预设内容；附件只登记文件名；连接、导入、修复、试跑和用量是演示；下载的是不可直接导入的示意 YAML。

## 3. 应保留的交互原则

1. 用户先选择类型；助手不能静默改成另一种类型。
2. 需求、具体配置和资源操作有明确确认入口。
3. 每个确认对象可定位到具体方案版本，不能只保存一个无上下文的布尔值。
4. 修改需求、配置或材料会使受影响的确认和测试失效。
5. 主流程缺失、关键冲突未解决或未确认时，搭建入口说明原因并阻止执行。
6. 执行状态来自后台，不以定时动画代替真实进度。
7. 用户能看到成功部分、失败部分、模拟依赖和待办。
8. 对话区用于沟通；工作台用于检查和操作，二者状态保持一致。
9. 未连接环境可以产出待验证文件，但不得显示“真实导入成功”。
10. 用量和费用使用实际记录；不可获得时显示未知，而非编造数字。

## 4. 可调整但需说明的部分

- 产品名称、颜色、字体、间距和图标。
- 工作台标签页数量及设置采用弹窗或独立页面。
- 流程预览的排布；首版不要求完整拖拽画布编辑器。
- 消息中的方案卡片和右侧页面之间的跳转方式。
- 同时展示的配置项数量，以及非关键选项的折叠方式。

这些调整不改变用户选择、确认、真实验证、保存进度和交付规则。

## 5. 原型检查脚本

1. 打开售后示例任务，查看需求说明并确认。
2. 查看具体模型、知识库和资源操作；编辑一项后重新确认。
3. 运行模拟生成，查看错误修复和样例结果；暂停后继续。
4. 查看交付说明，确认所有未验证／模拟位置可见。
5. 在对话中提出变更，检查任务回到待确认状态。
6. 新建任务，检查应用类型必须主动选择，未补齐需求不能确认。
7. 打开模型和环境设置，确认不接收真实 Key、不发送网络请求。
8. 上传参考文件，确认只登记名称，未假装完成解析。
9. 刷新页面，检查演示进度可恢复。浏览器存储不可用时应有保存提示。

以上仅用于评审原型。正式验收使用真实后台、模型和目标 Dify，不使用动画结果替代。
